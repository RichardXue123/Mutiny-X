# Flash → Unity 2D 复刻规范

版本：1.0 / 2026-09-15。适用目标：在明确的原版版本和验收范围内，还原可观察行为、画面和声音。

**交付单位是“有证据、可复现、已对照通过的一条行为”，不能只按类名、资源数量或功能名称计完成。** 规范不能证明绝无遗漏；它应让遗漏可被发现、定位并防止再次出现。

## 2. 资料和证据规则

每次对照记录：SWF/关卡 XML 指纹、Unity 提交及工作区改动、播放器/模拟器名称与版本、Unity 版本、分辨率、缩放、帧率、输入方式、随机条件。

### 证据分类

| 类型 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- |
| S：AS2 + 必要的 pcode | 条件、赋值、调用链、参数、继承覆盖 | 完整运行画面和播放器实际时序 |
| A：资源/时间轴 | symbol、帧标签、嵌套层级、注册点、音频资源 | 脚本执行后的运行时合成结果 |
| R：原版运行记录 | 指定场景实际行为、画面、声音及输入结果 | 没有触发的分支 |
| U：用户报告 | 必须纳入调查和验收的体验差异 | 所有武器/关卡都适用的泛化规则 |
| H：推测 | 下一步调查方向 | 已确认需求或验收通过 |

每条结论注明类别、文件+符号/函数+行号，或录像+时间点/帧号。行号只作定位，版本和符号共同确定证据。

遇到冲突，建立冲突项：双方证据、涉及版本、可能原因、最小复现场景、下一步判别方法。在完成核查前不把争议结论写成全局规则。反编译逻辑异常时查 pcode；模拟器与原始播放器可能不同，注明参考环境。Unity 现状不是原版行为的证据。

## 3. 全量清点：同时从原版和玩家操作出发

复用已有类、方法、事件、时间轴、symbol、关卡和音频索引。为原版入口建立映射：`来源 → 规则 ID → Unity 入口 → 用例`；每个入口都应标记已映射、待调查，或有证据说明不在范围内。再反查玩家可做的操作和看到的状态，避免只扫描源码名称而漏掉交互。

| 范围 | 必须清点的维度 |
| --- | --- |
| 回合/选人 | 首回合、未选人、切人、取消、行动前后、主动结束、死亡和胜负 |
| 武器 | 每种武器独立阶段、所有 override、操作、库存扣除、取消、碰撞、水、结束和跨回合状态 |
| 物理 | 单位、坐标轴、每 tick 更新顺序、重力、碰撞边界、摩擦、预测与正式运动 |
| UI | 面板生命周期、红蓝队、可用/不可用/悬停、文案、库存、字体、命中区域及显示延迟 |
| 角色/动画 | 每个角色、朝向、帧标签、循环、嵌套动画、帧脚本、受击/落水/死亡 |
| 关卡/空投 | XML 属性、层级、有效列、随机权重、落下、拾取、占用与回合影响 |
| 镜头/音频 | 触发、目标优先级、持续、打断、循环、静音、空间/音量设置 |
| 外围流程 | 菜单、暂停、重开、选关、解锁、存档、单/双人模式和 Player 构建 |

每个模块写明已覆盖集合与未覆盖集合。现有 18 个 XML 不自动等于原版全部关卡。不同武器或角色不能未经证据就视为等价；数量覆盖不能代替行为覆盖。

## 4. 行为规格：先描述转换，再实现

使用 [规格模板](Specs/BEHAVIOR_TEMPLATE.md)，每条规则至少包含：

1. 前置状态：队伍、角色、阶段、行动资格、装备、库存、动画和面板状态。
2. 输入事件：按下/移动/释放、坐标系、时机及输入是否被 UI 消耗。
3. 允许条件：包括权限、资源、锁定、运动中等条件。
4. 状态变化：哪次事件消耗什么；选择、瞄准、提交、结算必须区分。
5. 可观察结果：图像、文案、音效、镜头、对象、数值和触发 tick。
6. 拒绝与边界：重复点击、取消、零库存、死亡、阈值前/等于/后和特殊覆盖。
7. 原版证据、Unity 对应入口、用例和实际验证状态。

不把“每回合跳跃+武器”泛化成两个行动任意顺序。必须列转换表并核对每类武器。UI 应从已确认的状态派生显示；不能以图像是否灰色反推是否消耗行动。

### Flash 特有要求

- 同时阅读类脚本、主时间轴、MovieClip 帧脚本、事件绑定和动态 attachMovie 链接。
- 导出静态图不执行 AS2。可独立变状态的子元素必须保留状态资源/独立层，或有能完整表达这些状态的合成方案。
- 写明 symbol、帧标签、帧段、注册点、子元素变换和裁剪偏移。不得只记录“用了原图”。
- 固定模拟 tick 与渲染帧的关系；保留原始更新顺序。动画触发伤害、音效、结束事件必须进入时序规格。
- 随机对照不能仅给 Flash 和 Unity 相同种子：两端算法与随机调用顺序可能不同。记录并重放抽样结果/统一随机序列；做不到时明确哪些场景只能统计比较。

## 5. 三层验收和实际入口

### 武器专项复刻门槛

所有“复刻某个武器”“修复某个武器”或“继续下一个武器”的工作，必须执行 [`Specs/WEAPON_REPLICATION_WORKFLOW.md`](Specs/WEAPON_REPLICATION_WORKFLOW.md)。武器必须先按原版来源图追踪本体、父类、玩家/AI 调用者、物理、时间轴/资源、声音和回合；随后按路径写状态转换、25 Hz 顺序、显示契约和声音映射。只翻译单个 AS2 武器类、创建一个可见对象或完成编译，都只属于静态初版，不能声明已复刻。

对每个武器修复，必须补一个从生产入口驱动、能在修复前复现问题的回归用例。完成报告将静态确认、已实现、实际测试通过、待运行验证和已知差异分别列出；原版运行对照未执行时保持未完成状态。

| 层 | 操作 | 断言 |
| --- | --- | --- |
| 逻辑/模拟 | 驱动真实生产方法及模拟 tick | 行动资格、库存、对象、伤害、结束条件和事件顺序 |
| 输入/场景 | 在真实场景经生产输入路径执行同一操作序列 | UI 命中、角色选择、拖拽、面板回开、序列化和导入结果 |
| 原版对照 | 固定环境重放操作，保存双方日志/截图/录像/音频事件 | 数值、视觉、声音、镜头和节奏一致性 |

测试的期望来自原版证据，与生产计算独立。测试可以配置前置条件；触发行动时不能直接把 `CanThrow` 改为期望值后再断言它。纯公式自测只能作为计算检查，不计入实际行为通过数。

核心回合/UI 需要同时覆盖三层。纯资源条目可使用来源/导入检查及视觉对照，无须给每个文件制造一个无意义单元测试。

### 对照记录

- 输入：场景 ID、逻辑 tick、事件、按钮、坐标系和坐标；必要时记录同 tick 内事件顺序。
- 状态：tick、phase、team、selectedCharacter、canThrow、canShoot、weaponSelected、weaponLocked、库存、位置速度、inactivity。
- 表现：面板 visible/alpha/contentsActive、按钮样式键/帧标签、实际可点击状态、动画帧、镜头、音效事件。
- 先定位第一个分歧 tick，再检查后续影响；不要只比较最终“都能结束回合”。
- 枚举状态、布尔值、库存及事件顺序默认要求精确一致。数值误差须注明单位和依据，不能事后放宽到通过。
- 图像使用相同逻辑视口和关键状态，分别比较 UI 区域和场景区域。记录抗锯齿等允许误差；任何遮罩都要写明原因，不能遮掉待测按钮或文本。逻辑错误不得用像素误差容忍。
- 静音功能与声音触发均要验证；存在音频文件不代表播放时机正确。

## 6. 进度与完成门槛

逐规则分别记录“证据状态、实现状态、验证状态”；一个复合功能只有在全部必要子规则通过后才能标完成。

| 验证状态 | 含义 |
| --- | --- |
| 未执行 | 只有规格或验收步骤 |
| 失败 | 实际执行并观察到不符合预期，附记录 |
| 部分通过 | 明确哪些层或场景已通过，其余仍未执行/失败 |
| 通过 | 该规则要求的全部层、场景均有当前基线的实际通过记录 |
| 阻塞 | 缺少具体输入/环境，记录所缺事项 |

`TODO.md` 保留唯一工作队列；Specs 是详细规则及用例，不新建互相竞争的总清单。旧 `[x]` 不自动成为新规范下的行为验收通过。

每次完成必须提供：规则 ID、原版定位、修改入口、实际执行命令/操作、实际结果与证据位置、剩余差异。编译通过、资源齐全、已写人工步骤分别只证明其自身，不能替代玩法对照。

优先跑本次改动影响的用例与关联回归；最终交付再做范围内全流程/关卡/角色/武器验收。不要在相同基线上反复跑已通过检查却继续缺少关键对照。

## 7. 缺陷处理与版本维护

缺陷卡：`ID / 基线 / 前置条件 / 操作 / 原版期望+证据 / Unity 实际+证据 / 最早分歧 / 根因 / 影响规则 / 回归用例 / 状态`。

优先修复影响大量系统的回合、输入、更新顺序和资源合成问题。每修复一个缺陷补一个能检测该缺陷的用例，并记录修复前失败、修复后通过；不能执行时保留未执行状态。

新证据改变旧结论时，更新规格及冲突记录，并同步关联 TODO、测试期望、验收说明。不能让错误旧步骤继续作为工作入口。用户授权的操作扩展单列 EXT 条目；历史文档声称“已授权”时，应保留来源，不能当作更多扩展的授权。

## 8. 推荐执行顺序

1. 先完成 `TURN_ACTION_UI.md`：选人 → 正常菜单 → 跳跃 → 灰色跳跃+可用武器 → 使用武器 → 结算 → 下次本队回合重置。
2. 对这一条完整链路完成三层验收，建立可复用日志和输入格式。
3. 按各武器独立生命周期扩展，随后覆盖角色、空投、镜头、声音和外围流程。
4. 最后按已声明范围执行全量验收，输出通过项、失败项、未知项及明确扩展。
